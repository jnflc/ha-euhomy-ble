# Euhomy BLE for Home Assistant

Local Bluetooth control of **Euhomy portable compressor fridges** (CF45, CF-series with the
*Euhomy Smart* app) from Home Assistant. Works through any Bluetooth adapter or
[ESPHome Bluetooth proxy](https://esphome.io/components/bluetooth_proxy.html).

> **Status: early.** The protocol layer is verified against the hardware-proven implementation
> of [lyntoo/ha-euhomy-ble](https://github.com/lyntoo/ha-euhomy-ble) (written for the CFC-25) and
> against a simulated fridge, and the advertisement and GATT layout of a **CF45**
> (SKU CF001-45GR-DEEH) was checked with LightBlue. The data point (DP) map below comes from the
> CFC-25 and has **not yet been confirmed on a CF45**. If something does not match, the
> [diagnostics download](#troubleshooting) shows every DP your fridge reports.

## What you get

| Entity | Type | Notes |
|---|---|---|
| *Fridge* | Climate | on/off, target temperature (-20 … 20 °C), current temperature, preset **MAX** / **ECO** |
| Temperature | Sensor | internal temperature, for graphs and statistics |
| Battery voltage | Sensor | supply voltage as measured by the fridge (e.g. your car battery) |
| Battery protection | Select | low / medium / high cut-off level (config) |
| Display unit | Select | °C / °F on the fridge's own display (config) |
| Panel lock | Switch | locks the buttons on the fridge |

Fault codes (E1…E6) are shown on the fridge's display only; the firmware does not send them
over Bluetooth.

## Do I need a cloud account?

**Once, to look up a key. Never afterwards.**

The fridge is a Tuya Bluetooth device. Its Bluetooth traffic is encrypted with a *local key* that is
generated by the Tuya cloud when the fridge is added to the Euhomy Smart app. The key is not printed
on the fridge and is not readable over Bluetooth, so it has to be fetched from the cloud one time.
This integration never talks to any cloud: you paste three values into Home Assistant and from then
on everything is local over Bluetooth.

You need the fridge to be added to the **Euhomy Smart** app (that is a Tuya account you probably have
already) and a free developer account on [iot.tuya.com](https://iot.tuya.com).

### Looking up local key, device ID and UUID

1. Sign up at [iot.tuya.com](https://iot.tuya.com) and open **Cloud → Development → Create Cloud
   Project**. Industry and development method: *Smart Home*. Pick the data center of your region.
   Make sure the API product **IoT Core** is authorized.
2. In the project open **Devices → Link App Account → Add App Account**. A QR code is shown.
3. In the **Euhomy Smart** app scan that QR code (scan icon on the *Me* tab; the exact place may
   differ between app versions). Your fridge now appears in the project's device list.
4. Note the **Device ID** of the fridge from the list.
5. For **UUID** and **Local key**, open **Cloud → API Explorer → Device Management** and run the
   call that returns the device details (`GET /v1.0/devices/{device_id}`; it is called *Get Device
   Information* or *Query Device Details* depending on the platform version) with your device ID.
   In the result:
   - `id` is the *Device ID*
   - `uuid` is the *UUID*
   - `local_key` is the *Local key*

The local key stays valid until you remove the fridge from the app and add it again; then repeat
the lookup and use the *re-authenticate* prompt in Home Assistant.

Keep the local key private: together with Bluetooth range it gives full control of the fridge.

## Installation

**HACS:** *HACS → ⋮ → Custom repositories* → add `https://github.com/jnflc/ha-euhomy-ble` as
category *Integration* → download **Euhomy BLE** → restart Home Assistant.

**Manual:** copy `custom_components/euhomy_ble/` into your Home Assistant `config/custom_components/`
and restart.

Requires Home Assistant 2024.11 or newer (developed and tested against 2026.2) and a Bluetooth
adapter or proxy in range of the fridge.

## Setup

1. **Close the Euhomy Smart app completely.** A Tuya BLE device normally accepts only one
   connection at a time, so the fridge is invisible to Home Assistant while the app holds it.
2. *Settings → Devices & services → Add integration → Euhomy BLE*.
3. Pick your fridge from the list. Euhomy fridges advertise under the generic Tuya name **TY**, so
   if several appear, compare the address with the one shown by your proxy or by LightBlue.
4. Enter local key, device ID and UUID. Home Assistant connects once to verify them; wrong values
   are reported right away.

The integration holds a persistent connection (the fridge pushes changes immediately). To use the
phone app again, disable the integration entry (*⋮ → Disable*) and re-enable it afterwards.

> There is deliberately no automatic discovery: every Tuya Bluetooth gadget in the house advertises
> exactly like the fridge, so announcing all of them as "Euhomy" would be noise.

## Troubleshooting

| Symptom | Likely cause |
|---|---|
| "Could not connect" | Euhomy app still open, fridge off or out of range, proxy out of free connection slots |
| "The fridge did not answer" | wrong local key |
| "The fridge rejected the credentials" | wrong device ID or UUID, or the fridge was re-added to the app (new key) |
| Entities stuck on *unavailable* | the link dropped; Home Assistant reconnects as soon as the fridge advertises again |

**Diagnostics:** *Settings → Devices & services → Euhomy BLE → ⋮ → Download diagnostics* contains
every data point the fridge reported (id, type, value) with the credentials and address redacted.
Please attach it to an issue when a value looks wrong or an entity stays empty; that is exactly the
information needed to support another model.

**Debug log:**

```yaml
logger:
  logs:
    custom_components.euhomy_ble: debug
```

The log then contains each decrypted message. It does not contain the local key.

## Data points

Mapped on a Euhomy CFC-25 by pressing the buttons on the fridge and watching the reports
([lyntoo/ha-euhomy-ble](https://github.com/lyntoo/ha-euhomy-ble)); to be confirmed on the CF45.

| DP | Type | Meaning | Access |
|---|---|---|---|
| 101 | bool | power on / standby | R/W |
| 102 | enum | panel lock: 0 = unlocked, 1 = locked | R/W |
| 103 | enum | mode: 0 = MAX, 1 = ECO | R/W |
| 104 | enum | battery protection: 0 = low, 1 = medium, 2 = high | R/W |
| 105 | enum | display unit: 0 = °C, 1 = °F | R/W |
| 112 | int | internal temperature, °C | R |
| 114 | int | target temperature, °C | R/W |
| 117 / 119 | int | °F mirrors of 112 / 114 | R |
| 122 | int | supply voltage, mV | R |

## Protocol notes

What a CF45 shows in LightBlue, and what this integration relies on:

- advertises as local name `TY`, manufacturer data under company id `0x07D0`, service `0xA201`
  (all Tuya BLE)
- GATT: Device Information (`0x180A`) and a vendor service `0x1910` with *Module->Phone*
  (notify, read) and *Phone->Module* (read, write, write without response). The usual UUIDs are
  `0x2b10` / `0x2b11`; if a firmware uses different ones they are picked by their properties.
- Tuya BLE protocol v3: AES-128-CBC, keys derived from the first six characters of the local key
  (`MD5(key6)` for DEVICE_INFO, `MD5(key6 + srand)` afterwards), handshake DEVICE_INFO → PAIR →
  DEVICE_STATUS, data points as `[id][type][length][value]`. See the docstring of
  `custom_components/euhomy_ble/tuya_ble.py`.

## Development

```bash
python -m venv .venv && . .venv/bin/activate
pip install -r requirements_test.txt ruff
pytest
ruff check . && ruff format --check .
```

The tests cover the protocol (against a simulated fridge that implements the device side of the
handshake), the config flow, all entities and commands, reconnect behavior and diagnostics.
